01 / Start here

Local Perplexity Bridge

An experimental Windows application that serves a local API through an account signed in to Perplexity's website. WPF and WebView2 provide the desktop and isolated browser profiles; ASP.NET serves the loopback API. The harness supplies and executes local tools.

Source version: 0.5.0. Latest installed live verification: v0.3.4, Pro account, perplexity-claude55sonnetthinking. A new build from this source includes changes not present in that installed test binary. Review the test evidence before making capability claims.

Install and first connection

  • Use a trusted locally built Windows x64 installer, or extract the portable ZIP into a writable folder. The release script produces a self-contained .NET application; the WebView2 Runtime is still required. No GitHub binary release is implied by a source-code push.
  • Launch PerplexityLocalBridge.exe. Read the version badge and window title. Add a named account and complete website sign-in and any verification in the embedded browser.
  • Apply the account baseline in the Account setup section. Check the account, refresh models, and choose the API account/default model.
  • In API, leave OpenAI compatibility, Require a local API key, and Translate harness tool calls enabled. Default port is 8082. Create a named client key and copy it immediately: it is shown once. Save all settings.
  • Click Connect Perplexity + start API. Configure the harness with base URL http://127.0.0.1:8082/v1, local key, a discovered model, and a session-tracking extension.
  • Test a small prompt, then a real local write/read/edit cycle. Check actual tool output and the Sessions tab. A green process health response alone does not prove generation readiness.

Official Perplexity API keys and web subscriptions are separate products. This bridge has no separately billed API fallback and makes no claim of provider-supported subscription API access.

API quick start

import os
from uuid import uuid4
from openai import OpenAI

# Persist this identifier with your chat, and reuse it for tool results/resume.
session_id = str(uuid4())
client = OpenAI(
    base_url="http://127.0.0.1:8082/v1",
    api_key=os.environ["LOCAL_PERPLEXITY_KEY"],
    max_retries=0,
    timeout=180,
    default_headers={
        "X-Perplexity-Session-Id": session_id,
        "X-Perplexity-Project-Id": "example-project",
        "X-Perplexity-Project-Name": "Example%20project",
    },
)
reply = client.chat.completions.create(
    model="perplexity-web",
    messages=[{"role": "user", "content": "Reply with exactly OK."}],
)
print(reply.choices[0].message.content)

Use Authorization Bearer or x-api-key for the locally generated key. Revoke a key to stop that client. No-key mode remains loopback-only, but any local process able to reach the port can then request generation. Host/Origin checks and body limits still apply. Keep keys outside source control.

Sessions, models and failover

Every generation requires a stable harness session ID. User turns and tool-result exchanges share one mapped native thread. A new harness chat gets a different mapping. Restart/resume retains the original mapping. Session identity includes key and project: changing those changes the mapping scope. Each mapped session stays pinned to its original account. Viewing another account is independent of routing.

Optional failover tries eligible accounts once for explicit rate/usage limits when establishing a new conversation, within the original timeout. It does not substitute unavailable models, move existing threads, or retry ambiguous generation outcomes. Provider reset information is used where available; other timers are local retry delays.

Large contexts are transferred through native messages within a 39,000-character budget; setup fragments and execution stay in one thread and consume additional allowance. Unchanged context is reused; follow-ups send incremental history. Echo checks detect website input truncation. Native system-message priority and unlimited total context are unavailable.

Tool reliability and compatibility

The model returns a structured envelope which the bridge translates into OpenAI tool calls. The harness executes them locally and supplies results. Website artifacts do not prove local file creation. Prompt compliance can fail; inspect tool events and actual files before accepting a completion claim.

Version 0.4.0 recovery code can extract a single complete nonce-matching JSON envelope from surrounding prose and validate names, arguments, duplicate keys and supported schema constraints. For a completed invalid response, it permits one correction in the same mapped conversation and original timeout. This consumes an additional native request. It does not automatically rerun an ambiguous transport outcome or invent argument repairs. These changes have synthetic coverage; live recovery is not yet verified.

SSE is buffered until generation and validation finish. Token usage is null. max_tokens-style budgets are approximate prompt guidance, not enforceable output limits; begin with modest tasks and enough time for context transfer. Sampling parameters cannot be enforced. Unsupported explicit reasoning controls are rejected; choose a discovered thinking-model ID instead. Citation links are retained for ordinary prose and excluded from structured tool payloads. Web search follows the website behavior and is not guaranteed disabled.

Images, file uploads, audio, Responses API, native tool execution, strict structured-output guarantees, and dedicated Research/Labs are outside the supported first-release workflow.

Data, backup and removal

Application data lives under %LOCALAPPDATA%\LocalPerplexityBridge, even for portable execution. It includes settings/key hashes, isolated WebView2 profiles, profile metadata, logs and DPAPI-encrypted conversation continuation data and recent cached replies. Metrics record lengths rather than prompts. Never upload the data folder, browser profiles, raw transcripts or credentials to GitHub. Windows DPAPI data is tied to the user context; copying files is not a portable credential export.

Back up data locally with the app closed before upgrades. Preserve it when uninstalling if you need to resume sessions. Removing an account invalidates its local session access and leaves routing tombstones; it does not delete website conversations. Original Claude app files remain separate, and port 8082 permits coexistence with its endpoint when ports do not conflict.

LAN mode and repeat-copy keys (0.5.0)

In API, enable LAN access, choose the PC's assigned private IPv4 address, and click Save all settings. The address and full LAN URL are shown below the selector. Local 127.0.0.1 access remains available. LAN requires key authentication and accepts private IPv4 clients only, with exact Host matching and browser Origin requests blocked. A network change can require selecting a new address and saving again. HTTP traffic is unencrypted: use only a trusted LAN, or an encrypted tunnel. Do not forward this port on your router.

If Windows Firewall blocks another device, allow the app on Private networks. An administrator can create a scoped rule with New-NetFirewallRule -DisplayName 'Local Perplexity Bridge LAN' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8082 -Profile Private -RemoteAddress LocalSubnet. Adjust the port if changed. The app does not silently alter firewall settings.

Use the displayed LAN base URL on the remote harness and install updated helpers. Pi/OpenCode accept a configured RFC1918 private endpoint; DeepSeek's baseURL can name the PC's private IPv4 address. Keep real session tracking enabled. Tools execute on the computer running the harness. One generation runs at a time across clients.

New keys retain their authentication hash and a Windows-user DPAPI-encrypted copy. Select an active key and click Copy selected key any number of times, including after restarting the app. Older hash-only keys cannot be recovered: create a replacement, update clients, then revoke the older key. Clipboard access is explicit; secrets are not logged. Moving the settings to another Windows account does not make encrypted keys portable.

02 / Account setup

Configure every Perplexity account

Repeat this checklist for each distinct account. Recommended baseline: a dedicated bridge account. Account-wide personalization changes also affect ordinary website use.

  • In Accounts, choose Add account, assign a useful local label, and open Sign in / open Perplexity. Complete login and verification yourself in that profile's embedded browser. A login in Codex, Chrome, or another profile does not sign this profile in.
  • Verify the intended email and subscription in the website account menu. Never infer remaining allowance from a Pro badge or model list.
  • Open website Settings → Personalization. Set response length and headers/lists to Default. Paste the conditional instructions below. Occupation and company fields can remain empty; they are unnecessary for the bridge.
  • For dedicated bridge accounts, turn Use search history and Notes off under Memory. Do not delete existing conversations or stored memories as part of setup.
  • Disable unrelated custom skills, such as Content creation, for this baseline. Upload the bridge skill through Plugins → Add custom → Upload plugin or skill, or the older Customize → Skills → Create skill → Upload skill interface. Confirm its name and description on Installed.
  • Back in the app, click Check selected account, then Models → Refresh models from Perplexity. Choose only a discovered model, or the automatic option if manual selection is unavailable.
  • Enable Include in API routing and choose Use for API when this should be the default account. Viewing another profile does not change API routing. Save all settings.
  • Run the local endpoint test, then a harmless harness write/read/edit cycle. Verify real local tool events and disk contents. Record app version, explicit model ID, account tier, date, and results.

Conditional custom instructions

When a request explicitly identifies Local Perplexity Bridge and supplies a bridge_protocol response contract, follow that contract exactly. Return only the requested JSON object, with no Markdown fences or additional commentary. Use the current request's protocol identifier and only its declared caller tools.
The caller's tools execute on my local computer. Perplexity website artifacts and Computer tools are a separate environment. Request local file operations, commands, and application launches through the declared caller tools. Never substitute a website artifact for a local file.
A requested tool call is not a completed action. Claim success only after receiving a successful caller tool result. Do not invent results or claim local tools are unavailable merely because Perplexity cannot directly access Windows.
For these bridge requests, use the supplied conversation and current instructions for project state, rather than memories or other conversations. Acknowledge context-transfer fragments exactly as instructed and wait for the execution request. For all other conversations, respond normally.

Skills and connectors: verified boundaries

Skills are documented for Perplexity Computer, with task-based activation. Uploading this skill does not prove activation in the bridge's Search-mode transport, enforce JSON syntax, or grant local permissions. The latest successful tests were performed after the user reported applying this baseline; they do not isolate which setting helped.

Custom remote MCP connectors require HTTPS and support authentication. A cloud service cannot reach this PC's 127.0.0.1 endpoint. No remote connector or public tool relay is implemented by this app. Do not enter the local API URL as a remote connector expecting local shell access.

Sources checked 28 October 2026: Computer skills, remote connectors.

Multiple accounts

Keep one isolated browser profile per account and repeat the baseline in each account. Reordering changes new-request candidate order. Failover applies to recognized usage/rate limits for new conversations; existing sessions remain pinned to their original account. A local retry delay is not a provider quota-reset estimate. Reset pause clears the local timer only. Removing a profile invalidates access to its mapped sessions; it does not migrate them or delete website conversations. Free and Max generation remain unverified separately.

03 / Harness development

Build a harness integration

The extension's job is stable identity and provider configuration. The harness retains its tools, execution permissions, approvals, and tool-result loop. A skill alone cannot provide reliable session identity.

Wire contract

Send these headers on every generation request, including tool-result continuations, retries, and resumed sessions:

HeaderValue
AuthorizationBearer <local bridge key>
X-Perplexity-Session-IdPersistent unique harness conversation ID
X-Perplexity-Project-IdStable opaque project ID, e.g. SHA-256 of canonical workspace path
X-Perplexity-Project-NameURI-encoded display label

Session mappings are scoped to local key + project + session. Persist the session ID with the harness conversation. Generate a new ID for new chats and forks. Reuse it when resuming. Never derive identity from prompt text, generate it per HTTP call, or use a single provider-wide ID. Rotating the local key changes the mapping scope.

Equivalent body metadata fields are session_id, project_id, project_name. Explicit headers take precedence. Clients limited to base URLs can use /v1/sessions/<unique-session-id>; change that URL for every new chat. Conflicting scoped URL/header IDs are rejected. Missing identity returns session_id_required.

Minimal reusable adapter

import { createHash } from "node:crypto";
import { resolve, basename } from "node:path";

export function bridgeHeaders({ baseURL, apiKey, sessionId, workspace }) {
  const url = new URL(baseURL);
  if (url.protocol !== "http:" || !["127.0.0.1", "localhost", "[::1]"].includes(url.hostname))
    throw new Error("Expected local bridge URL");
  if (!sessionId) throw new Error("Persist a conversation ID before generation");
  const cwd = resolve(workspace);
  const identity = process.platform === "win32" ? cwd.toLowerCase() : cwd;
  return {
    Authorization: `Bearer ${apiKey}`,
    "X-Perplexity-Session-Id": sessionId,
    "X-Perplexity-Project-Id": createHash("sha256").update(identity).digest("hex"),
    "X-Perplexity-Project-Name": encodeURIComponent([...basename(cwd)].slice(0, 48).join(""))
  };
}

Hook this into the harness's request builder, restricted to its configured local Perplexity provider. Resolve workspace identity consistently across restarts; symlinks, path case, or relocating a project can change it. Do not send bridge credentials to arbitrary remote URLs. Fetch /v1/models with the local key and preserve IDs exactly. perplexity-web selects the app default; perplexity-auto requests website automatic selection. Do not hardcode paid models for Free profiles.

Tool loop

  • Send standard OpenAI messages and declared function tools, including valid JSON schemas. Enable Translate harness tool calls in the app.
  • Read returned tool_calls; arguments are JSON strings. Execute them using the harness's existing tool dispatcher and permission checks.
  • Append the assistant message containing those calls, then matching role: tool messages with each tool_call_id. Send the continuation with the same session/project headers.
  • Continue until the assistant produces a final response. Confirm file changes and command outcomes from actual tool results.

The bridge supplies its internal protocol nonce and validates the returned envelope. Do not implement your own fixed nonce or pre-wrap normal SDK messages. Streaming is buffered: a long pause before SSE is expected. Usage is null. Select a discovered thinking model by ID if desired; omit explicit reasoning controls. Disable automatic retries for ambiguous generation failures. Honor cancellation and surface errors instead of creating replacement conversations.

Pi reference

Source: perplexity-bridge.mjs. The app's App → Set up Pi session tracking installs it as ~/.pi/agent/extensions/perplexity-bridge.ts and configures the provider. Restart Pi or run /reload.

Developer install: node scripts/Install-PiIntegration.mjs from the repository root. This requires an existing perplexity-2-api provider in ~/.pi/agent/models.json; it installs the helper and refreshes models using the existing local key. The app setup is the easier initial configuration route.

The helper uses before_provider_headers, metadata fallback in before_provider_request, and after_provider_response for thread status. /perplexity-thread shows the linked thread; /perplexity-models refreshes choices. It uses Pi's session manager ID and workspace hash. Hook availability must be checked for the target Pi build. Latest live checks used Pi CLI 1.4.0; isolated tests disable unrelated Pi extensions, skills and MCP.

OpenCode reference

Copy perplexity-sessions.mjs to ~/.config/opencode/plugins/perplexity-sessions.ts, preserving its named export. Restart OpenCode. Configure provider ID perplexity-2-api, npm provider @ai-sdk/openai-compatible, and options.baseURL as http://127.0.0.1:8082/v1; store a generated local key through the harness's authentication flow. Populate model IDs from the bridge.

The plugin uses chat.headers, input.sessionID, input.model.providerID, and the project directory. Test hook compatibility against the installed OpenCode version. Hook fixtures and the compatible provider SDK passed; the latest suite did not run a full live OpenCode UI workflow.

DeepSeek Harness plugin

The DeepSeek provider bundle registers a dedicated perplexity-bridge adapter with the host LLM service. It includes authenticated model discovery, durable session headers, cancellation, disabled automatic retries, and translation for published rc.1 and current-source tool-result formats. See its README for Plugin Manager installation, environment configuration, auxiliary-call limitations and model-specific live evidence. Unlike the Pi/OpenCode helpers, this is a complete provider adapter.

Acceptance checklist

  • Same chat: user → tool call → tool result → follow-up retains one X-Perplexity-Thread-Id.
  • Restart/resume retains that thread; new chat and fork get distinct threads.
  • Concurrent chats and two workspaces remain isolated. Cancellation does not silently start a replacement request.
  • Missing identity and unavailable model fail clearly; no automatic model substitution.
  • Real write/read/edit/shell actions succeed locally; missing-file errors remain errors.
  • Model refresh uses authenticated discovery; revoked local keys are rejected.
  • Inspect /v1/bridge/sessions and actual local files. A plausible assistant claim alone is not a passing test.

Use the existing Pi/OpenCode hook tests and live SDK scripts as references. Record model ID, tier, app version, harness version, prompt sizes, settings baseline, time, and whether the check was synthetic or live. Keep raw account/thread/credential artifacts out of commits.
